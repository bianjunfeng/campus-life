```

│                   campus-life-backend                    │
```

## 二、微服务拆分可行性

### 2.1 模块耦合度分析

```
耦合度热力图:
                    user  auth  forum  merchant  voucher  payment  message  search  admin
user                -     中    低     低        低      低      低      低     高
auth                中    -     低     低        低      低      低      低     中
forum               低    低    -      低        低      低      中      中     高
merchant            低    低    低     -         高      低      低      低     中
voucher            低    低    低     高        -       高      低      低     高
payment            低    低    低     低        高      -       中      低     高
message            低    低    中     低        低      中      -       中     中
search             低    低    中     低        低      低      中      -      中
admin              高    中    高     中        高      高      中      中     -
```

**关键发现**：
| 耦合类型 | 模块对 | 风险等级 |
|---------|-------|---------|
| **共享实体** | voucher ↔ payment (VoucherOrder) | 🔴 高 |
| **星型耦合** | admin → 所有业务模块 | 🔴 高 |
| **跨域事务** | payment + voucher + user (钱包) | 🔴 高 |
| **事件解耦** | forum ↔ search, forum ↔ message | 🟢 低 |

### 2.2 建议拆分方案

#### 方案 A：渐进式微服务拆分（推荐）

```
阶段一：独立 AI 和搜索服务（风险低）
├── ai-service        → 已有独立项目
└── search-service   → 已有 Kafka 事件驱动基础

阶段二：抽离管理后台（降低 admin 耦合）
└── admin-gateway    → 仅做 API 聚合，无业务逻辑

阶段三：核心域拆分（风险高）
├── user-service     → 用户 + 认证 + 钱包
├── forum-service    → 论坛 + 评论 + 举报
├── voucher-service   → 优惠券 + 秒杀 + 订单
├── payment-service  → 支付 + 退款 + 对账
└── merchant-service → 商户 + 认证

阶段四：通用域拆分
├── message-service  → 消息 + 通知
└── file-service     → 文件存储
```

#### 方案 B：DDD 改造优先（保守策略）

```
保持单仓架构，先进行 DDD 分层改造：
├── 限界上下文划分（BC）
├── 聚合根重构（Aggregate Root）
├── 仓储模式引入（Repository）
├── 领域事件完善（Domain Event）
└── 等待架构成熟后再考虑服务拆分
```

## 三、DDD 实施可行性

### 3.1 当前与 DDD 差距

| DDD 分层 | 当前实现 | 符合度 |
|---------|---------|--------|
| **Domain Layer** | 实体仅为 `@Data` POJO，无领域逻辑 | 20% |
| **Application Layer** | Controller → Service 直接调用 | 60% |
| **Infrastructure** | MyBatis Mapper 混杂 | 50% |
| **Interface Layer** | Controller + 少量 DTO | 40% |

## 四、技术挑战与工作量

### 4.1 分布式事务挑战

**现状**：
```java
// 当前单一数据库事务
@Transactional
public void payByWallet(Long userId, BigDecimal amount) {
    userWalletMapper.deductBalance(userId, amount);  // user 模块
    voucherOrderMapper.updateStatus(orderNo, PAID);  // voucher 模块

```

**拆分后需要**：
```
Saga 编排 或 Seata AT 模式
```

## 五、转型路径建议

### 5.1 渐进式转型路线图

```
                    传统单块
                       │
                       ▼
         ┌─────────────────────────┐
         │   第一阶段：DDD 试点     │  ← 3-6 个月
         │   · Voucher 模块试点    │
         │   · 聚合根重构         │
         │   · 领域事件引入       │
         └───────────┬───────────┘
                     │
                     ▼
         ┌─────────────────────────┐
         │  第二阶段：服务拆分     │  ← 6-12 个月
         │  · AI/Search 先行      │
         │  · Message 独立        │
         │  · Admin 门面化        │
         └───────────┬───────────┘
                     │
                     ▼
         ┌─────────────────────────┐
         │  第三阶段：核心域拆分    │  ← 12-18 个月
         │  · User/Auth 服务       │
         │  · Forum 服务           │
         │  · Voucher/Order 服务  │
         │  · Payment 服务        │
         └───────────┬───────────┘
                     │
                     ▼
              ┌───────────────┐
              │  微服务架构完成 │
              └───────────────┘
```

### 5.2 转型策略选择

| 策略 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **DDD 优先** | 业务复杂但团队 DDD 经验不足 | 风险可控，逐步演进 | 周期长 |
| **微服务优先** | 团队有微服务经验，业务相对简单 | 快速获得微服务收益 | 风险高 |
| **两阶段法** | 期望平衡风险和收益 | 兼顾两者优点 | 需两次重构 |

**推荐：两阶段法**
1. **第一阶段**：DDD 改造 voucher + payment 模块（3-6 月）
2. **第二阶段**：基于 DDD 成果进行服务拆分（6-12 月）

### 风险提示

```
🔴 高风险：分布式事务（支付+钱包场景）
🔴 高风险：聚合根重构（Post 贫血严重）
🟠 中风险：VoucherOrder 跨模块共享
🟠 中风险：Admin 模块过度耦合
🟢 低风险：AI/Search 服务已有独立趋势
```

### 建议优先级

| 阶段 | 行动项 | 预期收益 |
|------|--------|---------|
| **立即** | VoucherOrder 归属权统一 | 降低耦合 |
| **3个月内** | Admin 模块瘦身 | 解耦核心 |
| **6个月内** | Voucher 模块 DDD 试点 | 积累经验 |
| **12个月内** | AI/Search 服务独立部署 | 降低复杂度 |

---

**结论**：项目具备微服务/DDD 转型的基础，但建议采用**渐进式策略**，优先解决高耦合问题（VoucherOrder归属、Admin瘦身），再逐步推进架构演进，避免大爆炸式重写带来的业务风险。
